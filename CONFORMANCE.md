# tessera-kit conformance vectors

This document is the checklist for a second implementation (a Rust/WASM port,
or any other clean-room re-implementation) of the `KFLT` format and the
related canonical byte constructions in `PROTOCOL.md`. It lists every frozen
vector file under `vectors/`, what it proves, how to check your own
implementation against it, and — as important — what these vectors do **not**
cover.

If your implementation passes every check in this document, it is
byte-compatible with `@forgesworn/tessera-kit` for everything these vectors
exercise. This is a **necessary**, not sufficient, condition: a vector suite
proves agreement on the cases it contains, not universal correctness — see
"What isn't covered" below.

For what `format_version`/the signing-digest domain tag/error codes each
version independently, what a hypothetical v2 would be free to change, and
how a verifier rejects an unknown version, see
**[PROTOCOL.md §11, "Evolution / versioning"](./PROTOCOL.md#11-evolution--versioning)**
— that section states the upgrade/compatibility policy this conformance
checklist assumes.

## How to run the checks (this repo's own implementation)

```bash
npm run build          # compiles src/ -> dist/, which the checker imports
npm run vectors:check  # node ./scripts/check-vectors.mjs
```

`scripts/check-vectors.mjs` is itself the authoritative description of how
each vector `kind` is checked — read it alongside this document. It exits
non-zero and prints every mismatch on failure; a passing run prints the
number of vector files and individual assertions checked.

## How to check a NEW (e.g. Rust) implementation

There is no generic runner for a non-JS implementation — `check-vectors.mjs`
only drives this repo's own `dist/`. To validate a port:

1. Implement the construction described in `PROTOCOL.md` for the vector
   `kind` you're targeting (start with `filter`/`filter-set`/`filter-large` —
   the KFLT codec + Binary Fuse 16 construction — since everything else
   builds on it).
2. For each vector file of that `kind`, feed your implementation the frozen
   inputs (`memberKeysHex`/`opts`, or the documented member-generation rule
   for `filter-large`) and compare your output against the frozen fields
   (`serializedBlobHex`, `geometry`, `blobSha256Hex`, `membership`, etc.) —
   the same fields `check-vectors.mjs` compares against `dist/`'s output.
3. A mismatch on `serializedBlobHex` (or `blobSha256Hex`) means your
   construction diverges somewhere upstream: check `geometry` first (does
   your `segmentLength`/`segmentCount`/`arrayLength`/`seed`/`attempts` match?
   — see `kflt-sizes.golden.v1.json` and `kflt-retry-seed.golden.v1.json`)
   before assuming the peel/fingerprint-assignment step is at fault.

## Deterministic member-generation rule

Several vectors (`filter-large`, and `filter-set`'s larger cases) need many
member values. Rather than storing thousands to hundreds-of-thousands of
64-hex strings inline, they are generated by ONE documented, deterministic
rule, so any implementation can reproduce the exact same member list without
reading it off the vector file:

```
member_i = hex( sha256( utf8("tessera-vec:" + i) ) )    for i in [0, memberCount)
```

`i` is the decimal string representation of the integer index (`"0"`, `"1"`,
… `"99999"`), concatenated directly onto the ASCII prefix `"tessera-vec:"`
before UTF-8 encoding and hashing. This rule is informational metadata on
`filter-large` vectors (field `memberGenerationRule`) and is not itself
re-derived by `check-vectors.mjs` from a formula string — the checker's
`vecMember` function *is* the reference implementation of this rule; a port
must match its output byte-for-byte.

A related, but DISTINCT, rule generates non-member ("absent") probe values
used in samples:

```
absent_tag = hex( sha256( utf8("tessera-vec-absent:" + tag) ) )
```

where `tag` is an arbitrary distinguishing string (e.g. `"large-10000-3"`) —
this rule only needs to produce values that are (with overwhelming
probability) NOT in the member set; its exact tag scheme is not itself a
frozen contract, only the resulting hex values recorded in each vector's
`sampleAbsent`/`membership.absent` field are.

## Vector files and their `kind`

| File | `kind` | Proves |
|---|---|---|
| `kflt.golden.v1.json` | `filter` (implicit — no `kind` field; predates it) | The original frozen KFLT byte layout, n ≤ 8 (`arrayLength` = 24). Rebuild → serialize must equal `serializedBlobHex` byte-for-byte; the frozen bytes must also `parseFilter` and match `membership`. **Contains no signature** — unaffected by the §4 signing-context change. |
| `kflt-sizes.golden.v1.json` | `filter-set` | An array of `filter`-shaped `cases` at n = 0, 1, 2 (degenerate-n / §2.4 guard input), n = 3 and n = 9 (the two smallest `segmentLength` transition points, 4→8 and 8→16), n = 100, n = 1000 (realistic sizes, full blob hex). Each case also freezes `geometry` (`segmentLength`, `segmentCount`, `arrayLength`, `seed`, `attempts`). |
| `kflt-retry-seed.golden.v1.json` | `filter` | n = 829 — found by an exhaustive sweep (n = 1..20000, members from the deterministic rule above) for the smallest input whose Binary Fuse 16 construction needs a **seed retry** to converge (`seed_0` fails to peel; `next32(seed_0)` succeeds). `geometry.attempts = 2`. This is the vector requested by "search for an input needing ≥1 seed retry and freeze it" — see the note on reachability below. |
| `kflt-large-10000.golden.v1.json` | `filter-large` | n = 10000. No full member list or full blob hex (would be ~640 KB / ~25.7 KB respectively) — stores `geometry`, `blobSha256Hex`, and 20 present + 20 absent sample values, and the `memberGenerationRule`. |
| `kflt-large-100000.golden.v1.json` | `filter-large` | n = 100000. Same shape as above (full member list would be ~6.4 MB; full blob ~232 KB). |
| `reject.golden.v1.json` | `reject` | `parseFilter` MUST throw on every listed malformed blob (truncated, bad magic, bad version, invalid/unsupported type or fingerprint-bits, bad geometry, oversized declared length, length mismatch, epoch overflow, reserved flags, non-power-of-two band), with `error.code` (a `TesseraErrorCode`) EXACTLY matching the case's `expectedErrorCode` — the PRIMARY, strict assertion (item 3: typed errors; see `PROTOCOL.md` §9's error-codes table). `expectedErrorSubstring` is kept only as human-readable documentation and is not itself checked. |
| `signed-blob.golden.v1.json` | `signed-blob` | A fully-signed KFLT blob (§4) that must verify via `verifyAndParseFilter` against its `pinnedPubkeyHex` **and** `context`. Includes `digestHexIndependent`, hand-checked against `node:crypto` (not this package's own `@noble/hashes`), and `mustRejectContext` — the SAME blob+sig checked against a different, well-formed context MUST be rejected (the context-binding must-reject case, §4.1/§4.3). |
| `capability.golden.v1.json` | `capability` | The `./capability` canonical preimage/digest/signature (§5), independent of the signing-context change (capabilities are not filter-signature blobs and carry no `context`). |
| `decoy-seed.golden.v1.json` | `decoy-seed` | The per-epoch decoy-seed derivation formula (§2.8) plus `deriveDecoys` output. |
| `decoy-padding.golden.v1.json` | `filter` (implicit — no `kind` field) | Same shape as `kflt.golden.v1.json`, but with a fixed `decoySeedHex` and `padToBucket:true`: proves the per-epoch decoy-seed derivation is wired end-to-end through `buildMembershipFilter` (not just correct as a standalone formula — see `decoy-seed.golden.v1.json`). |
| `keyed-member-key.golden.v1.json` | `keyed-member-key` | `memberKey(pubkeyHex, saltHex)`, keyed and open forms, plus must-reject cases (empty/malformed salt). |

## What a second implementation MUST pass

At minimum, to claim KFLT byte-format compatibility:

1. **Geometry** (§2.4): reproduce `segmentLength`, `segmentCount`,
   `arrayLength` for every `n` in `kflt.golden.v1.json`, `kflt-sizes.golden.v1.json`,
   `kflt-retry-seed.golden.v1.json`, and the two `filter-large` vectors.
2. **Key hashing + mix + slot indices** (§2.1–2.3) and **peel + fingerprint
   assignment** (§2.5): reproduce `serializedBlobHex` byte-for-byte for every
   `filter`/`filter-set` case, and `blobSha256Hex` for every `filter-large`
   case.
3. **Seed retry schedule** (§2.2): reproduce the EXACT seed
   `kflt-retry-seed.golden.v1.json` converges to (`0x049de525`, after exactly
   one retry) — not merely SOME seed that happens to peel. A construction
   that retries in a different order, or accepts a different seed as
   "first success," will diverge here even if its own output is internally
   self-consistent.
4. **`parseFilter`'s hostile-input rejection** (§3.1): reject every case in
   `reject.golden.v1.json`, structurally for the same reason (ideally the
   same error code once your port has an equivalent typed-error contract).
5. **The signing digest, bound to `context`** (§4.1/§4.3): reproduce
   `digestHexIndependent` and the embedded signature's validity in
   `signed-blob.golden.v1.json`, AND reproduce the reject outcome for
   `mustRejectContext`.
6. **The capability canonical bytes** (§5.2) and **`memberKey`** (§1): pass
   `capability.golden.v1.json` and `keyed-member-key.golden.v1.json`.
7. **Decoy derivation** (§2.8): pass `decoy-seed.golden.v1.json` and
   `decoy-padding.golden.v1.json`.

## The degenerate-n guard (§2.4) is not exercisable as written

§2.4's pseudo-code includes a guard: after computing `segmentCount` and
`arrayLength` from the capacity/segmentLength formulas, if
`arrayLength < segmentLength * ARITY`, both are recomputed from the clamped
minimum. Reading the formula in isolation, this reads like it exists to
handle a real degenerate case at small `n`.

**In practice it is unreachable.** The step immediately before it already
clamps `segmentCount = max(1, floor((arrayLength + segmentLength - 1) /
segmentLength) - (ARITY - 1))`, and `arrayLength` is then RECOMPUTED as
`(segmentCount + ARITY - 1) * segmentLength`. Since `segmentCount >= 1`
always holds after that clamp, `arrayLength >= (1 + ARITY - 1) *
segmentLength = ARITY * segmentLength = minArray` holds unconditionally — the
`arrayLength < minArray` guard condition can never be true. We confirmed this
by an exhaustive sweep of `n` from 0 to 2000 (well past every practical case
and every `segmentLength` transition in that range): the guard branch never
fires for any of them.

We kept the guard in the spec prose (§2.4) and in `fuse.ts`'s implementation
— removing dead code that a byte-for-byte port might still choose to
implement (defensively, or for parity with a reference C implementation that
has the same guard) is out of scope for this documentation pass, and the
guard being unreachable is itself the useful fact to document: **a port does
not need to find an input that exercises it, because none exists under the
current formula.** `kflt-sizes.golden.v1.json`'s `n=0`/`n=1`/`n=2` cases pin
the exact boundary values (`arrayLength = 12 = segmentLength(4) * ARITY(3)`
— the guard condition is `false` by exactly zero, i.e. equality, not
inequality) so a port can confirm it reaches the identical numbers via
whatever path (guarded or not) it takes.

## What isn't covered

- **Hash-level dedup (§2.5, the M1 audit fix) cannot be vectored naturally.**
  `BinaryFuse16.build` de-duplicates by 64-bit `keyToU64` hash, not by key
  string, to defend against two DISTINCT 64-hex member-key strings that
  happen to collide on their 64-bit hash (found by a ~2^32 targeted birthday
  search, not achievable by chance in a frozen fixture). We cannot include a
  vector exercising this path without either (a) running that ~2^32 search at
  vector-generation time to actually find a colliding pair — expensive, and
  the resulting "found" pair would still just be two arbitrary-looking hex
  strings with no illustrative structure — or (b) hand-constructing two
  strings that hash-collide, which is exactly as expensive. `src/fuse.test.ts`
  covers this path with a **unit test** that injects a synthetic collision by
  testing the dedup logic directly, rather than via a real found collision;
  that test, not a vector, is the executable spec for this behaviour. A port
  should implement the SAME hash-level dedup (matching the Lemire reference
  C's `binary_fuse_sort_and_remove_dup`) but cannot be conformance-tested
  against a frozen byte vector for the collision case specifically.
- **The 20-bit and 32-bit fingerprint / xor(2) / cuckoo(3) reserved values**
  (`types.ts`, narrowed in item 4 of the pre-publish pass) have no vectors,
  because they have no implementation — `filter_type` and `fingerprint_bits`
  outside `{1, 16}` are reserved wire values with no defined array layout or
  construction algorithm yet. `reject.golden.v1.json` covers `parseFilter`
  correctly rejecting them as *unsupported* (not merely *invalid*).
- **Performance/scaling behaviour above n = 100000** is not vectored — the
  `filter-large` vectors exist to catch a *correctness* divergence at
  realistic-to-large scale, not to benchmark construction time or memory (see
  `scratchpad/bench.mjs`-style benchmarking, which is a separate,
  non-frozen concern).
- **Cross-language float formula reproduction is only spot-checked, not
  exhaustive.** §2.4's geometry uses `Math.log` / `Math.round`, which are
  IEEE-754 double operations expected to be bit-identical across conformant
  runtimes (JS, Rust `f64`, Go `float64`) for the specific inputs these
  vectors use, but the vector suite does not attempt to prove this for every
  possible `n` — only for the specific `n` values frozen here. A port
  targeting a platform without IEEE-754 doubles (e.g. a fixed-point or
  arbitrary-precision environment) would need additional verification beyond
  what this suite provides.
- **The `filter-large` vectors' `sampleAbsent` values are not proof of
  no-false-positive** — they are 20 curated non-member probes per vector,
  confirmed (at generation time) not to false-positive against that specific
  build. At the 16-bit design point (`p ≈ 2^-16`, PROTOCOL.md §7.1) a
  different, larger, or randomly-chosen absent sample could occasionally
  contain a false positive; that is expected behaviour, not a conformance
  failure, and `src/properties.test.ts` (not a frozen vector) is where the
  empirical false-positive RATE is checked statistically.
